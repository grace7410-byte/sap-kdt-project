### [04] 회계계정결정 — 전기키 F4 선택 시 차/대변 자동 채움 (`additionalBinding`, 어제 잔여 work) 

지금은 저장할 때(차/대변을 작성하지 않더라도) 자동 매핑되는 것까지는 구현되어 있는데, 이번에는 `@Consumption.valueHelpDefinition`의 `additionalBinding` 기능을 활용해서 F4 팝업에서 행을 선택하는 순간 그 행의 다른 컬럼 값을 화면의 다른 필드에 자동으로 꽂아주는 기능을 적용할 차례.

**1. 서치헬프 CDS 수정 — Shkzg용 컬럼 추가**

같은 소스 컬럼(`DomainText`)을 다른 별칭으로 한 번 더 select할 수 있다는 점을 활용해서, [`ZI_B07_BSCHL_F4`](../../reference/00_common-searchhelp.md) · [코드 보기](../../src/00_common-searchhelp/cds/ZI_B07_BSCHL_F4.ddls.asddls)에 `BschlText` 아래로 컬럼을 하나 더 추가함.

```abap
@Search.defaultSearchElement: true
@UI.selectionField: [{position: 20}]
@EndUserText.label: 'Posting Key Description'
DomainText  as BschlText,
// additionalBinding의 타겟 필드
// 동일한 소스 컬럼을 다른 별칭으로 한 번 더 select 가능하다!
@EndUserText.label: 'Debit/Credit'
DomainText  as ShkzgOut
```

**2. Root Projection View에서 additionalBinding 연결**

전기키 쪽에 additionalBinding으로 차/대변 필드(Shkzg)를 추가. `element`는 서치헬프 안에서의 필드명(`ShkzgOut`), `localElement`는 여기(화면)에서 그 값을 받을 필드(`Shkzg`)를 가리킨다. `usage: #RESULT`는 "F4에서 이 행을 고르면 그 값으로 로컬 필드를 채워라", `usage: #FILTER`는 "로컬 필드에 이미 들어있는 값으로 후보를 좁혀라"는 뜻으로 서로 반대 방향이다.

관련 오브젝트: [`ZC_B07_T030`](../../reference/04_account-determination.md) · [코드 보기](../../src/04_account-determination/cds/ZC_B07_T030.ddls.asddls)
```abap
/*********  전기키  ************/
@Consumption.valueHelpDefinition: [{
  entity: { name: 'ZI_B07_BSCHL_F4', element: 'Bschl' },
  additionalBinding: [
    { element: 'ShkzgOut', localElement: 'Shkzg', usage: #RESULT }
  ]
}]
@ObjectModel.text.element: ['Bsctx']
@UI.textArrangement: #TEXT_FIRST
Bschl,
Bsctx,

/********* 차/대변 (이제 자동으로 채워지므로 Readonly 권장) ************/
@UI.readOnly: true
Shkzg,
Shktx,
```

🧪 테스트: 값이 비어있는 상태에서 전기키 31을 선택하면, 바로 그 자리에서 차/대변 필드에 31에 맞는 값(H, 대변)이 자동으로 채워지는 것 확인.

**3. 기존 플랜트→저장위치 케이스와 비교 검토**

00번 공통문서에 나온 "플랜트가 정해지면 저장위치는 그 플랜트에 속한 것만" 케이스가 `#FILTER` 용도의 예다.

```sql
// 저장위치 서치헬프 CDS에 Werks 필드를 노출시켜 두고
@Consumption.valueHelpDefinition: [{
  entity: { name: 'ZI_B07_LGORT_F4', element: 'Lgort' },
  additionalBinding: [
    { element: 'Werks', localElement: 'Werks', usage: #FILTER }
  ]
}]
Lgort,
```

예전에 플랜트-저장위치 관계에서도 `#RESULT`와 `#FILTER`를 크로스로 걸어보려다 보류한 적이 있다. 저장위치명 값 자체가 중복되는 경우가 많아, 본사 플랜트를 제외하면 필터를 걸어도 후보 목록이 실질적으로 달라지지 않았기 때문이다(혹은 애초에 크로스 방향이 아니라 플랜트-저장위치가 서로를 필터링해주는 양방향 구조를 의도했던 것일 수도 있다).

이번 전기키-차/대변 관계는 상황이 다르다. 하나의 차/대변 값(예: H, 대변)에는 전기키가 다수 매핑되지만, 하나의 전기키(예: 31)는 반드시 하나의 차/대변 값에만 대응된다. 전기키 → 차/대변 방향이 항상 1:1로 명확하므로, `#RESULT`를 건 이번 방향은 문제없이 작동한다.

반대 방향(차/대변 → 전기키)으로 필터를 걸려면 `zi_b07_shkzg_f4` 서치헬프 자체를 손봐야 한다. 지금 이 뷰는 `ZDB07SHKZG` 도메인(S/H 값)만 보고 있어 `Bschl`과 매칭할 필드가 아예 없다. (1) `Bschl` 필드를 이 서치헬프에 추가하고, (2) 그 값으로 `ZDB07BSCHL` 도메인 데이터를 다시 끌어와, (3) `Shkzg`와 연결해야 하는 번거로운 구조다. `Shkzg` 필드는 이미 Readonly라 사용자가 F4로 값을 바꿀 일도 없어 실익이 크지 않다고 보고, **이번 건은 보류**한다..

### 강사 피드백 리뷰
KDT CL2 강사님께서 01~04 모듈 전체에 대한 피드백을 주셨다. 반드시 수정해야 할 사항은 아니고, 그냥 두는 게 낫다고 판단되면 그대로 둬도 된다는 전제였다.

- **[01] 자재관리:** ① 자재타입-평가클래스 불일치 저장 허용됨(체크 필요) ② 표준가격 0으로 저장 가능(체크 필요) ③ 자재 생성 시 자재코드 서치헬프가 있는데 필요한지 의문 ④ 자재명 없어도 저장됨(의도한 거면 무관)
- **[02] FI계정관리:** ① 중복 계정 생성됨 ② 조정계정유형/회사코드/통화/계정명 미입력해도 저장됨(의도한 거면 무관) ③ 존재하지 않는 회사코드/통화/조정계정유형 입력해도 저장됨
- **[03] 벤더관리:** ① 공급업체/계정에 Value Help 있으면 좋겠음 ② 구매정보 구매조직 필드 라벨 중복 ③ 신규 벤더 생성 시 거래종료 옵션이 필요한지 의문 ④ 계정/구매조직/최소주문금액 미입력해도 저장됨(의도한 거면 무관)
- **[04] 회계계정결정관리:** ① 자재평가/전기키/차대변에 존재하지 않는 데이터 저장됨 ② 해당 필드들 미입력해도 저장됨(의도한 거면 무관) ③ 순번이 Key라 이동유형+회계결정코드+평가클래스+계정 조합 중복 체크가 필요해 보임

이 중 **오늘은 [01] 자재관리 피드백만 반영**했고, [02]~[04]는 리뷰만 하고 아직 코드에 반영하지 않음(8/26 예정).

### [01] 자재관리 — 피드백 1-1: 자재타입 ↔ 평가클래스 매핑 검증
FS 명세 기준으로 매핑 구조를 다음과 같이 정리함: FERT(완제품)→7920, HALB(반제품)→7900, HAWA(상품)→3000, ROH(원자재)→3000, HIBE(소모품)/VERP(포장재)→3300(비평가자재). 자재유형 6개에 평가클래스 4개만 나오는 건 FS 명세상 소모품/포장재가 비평가자재(3300)로 묶이기 때문에 정상적인 설계로 판단.

관련 오브젝트: [`ZR_B07_MARA`](../../reference/01_material-mgmt.md) · [코드 보기](../../src/01_material-mgmt/bimp/zbp_r_b07_mara.clas.abap), BDEF: [코드 보기](../../src/01_material-mgmt/bdef/ZR_B07_MARA.bdef.asbdef)

기존 `validation CheckBklas on save { create; update; field Bklas; }`를 아래처럼 수정:

```abap
validation CheckBklas on save { create; update; field Bklas, Mtart; }
```

이미 input 체크 로직 쪽에서 자재타입/평가클래스 initial 여부는 확인하고 있음(기존 코드):

```abap
IF ls_mara-Mtart IS INITIAL.
  APPEND VALUE #( %tky = ls_mara-%tky ) TO failed-zr_b07_mara.
  APPEND VALUE #( %tky = ls_mara-%tky
                  %element-Mtart = if_abap_behv=>mk-on
                  %msg = new_message( id = 'ZMSGE_B07'
                                      number = '015'
                                      v1 = 'Material Type'
                                      severity = if_abap_behv_message=>severity-error ) )
      TO reported-zr_b07_mara.
ENDIF.
IF ls_mara-Bklas IS INITIAL.
  APPEND VALUE #( %tky = ls_mara-%tky ) TO failed-zr_b07_mara.
  APPEND VALUE #( %tky = ls_mara-%tky
                  %element-Bklas = if_abap_behv=>mk-on
                  %msg = new_message( id = 'ZMSGE_B07'
                                      number = '015'
                                      v1 = 'Valuation Class'
                                      severity = if_abap_behv_message=>severity-error ) )
      TO reported-zr_b07_mara.
ENDIF.
```

> 메시지 [`015`](../../src/message-class.md#015): "Field &1 is required and cannot be empty."

기존 `CheckBklas`는 평가클래스 값이 FS 요구 범위(3000/3300/7900/7920)를 벗어나는지만 체크하고 있었는데, `FIELDS ( Bklas Mtart )`로 필드를 추가하고 아래 IF문을 첫 번째 IF문(ENDIF) 바로 다음에 추가함. 메시지 처리 내용이 자재타입/평가클래스 조합만 다를 뿐 동일해서, 조합별로 개별 IF문을 만들지 않고 하나의 조건식으로 정리함.

```abap
  IF ( ls_mara-Bklas = '3000' AND ls_mara-Mtart <> 'ROH' AND ls_mara-Mtart <> 'HAWA' )
    OR ( ls_mara-Bklas = '3300' AND ls_mara-Mtart <> 'HIBE' AND ls_mara-Mtart <> 'VERP' )
    OR ( ls_mara-Bklas = '7900' AND ls_mara-Mtart <> 'HALB' )
    OR ( ls_mara-Bklas = '7920' AND ls_mara-Mtart <> 'FERT' ).
    APPEND VALUE #( %tky = ls_mara-%tky ) TO failed-zr_b07_mara.
    APPEND VALUE #( %tky = ls_mara-%tky
                    %element-Bklas = if_abap_behv=>mk-on
                    %msg = new_message( id = 'ZMSGE_B07'
                                        number = '022'
                                        v1 = ls_mara-Mtart
                                        v2 = ls_mara-Bklas
                                        severity = if_abap_behv_message=>severity-error ) )
        TO reported-zr_b07_mara.
  ENDIF.
```

> 메시지 [`022`](../../src/message-class.md#022): "A material of type &1 cannot have a valuation class of &2."

### [01] 자재관리 — 피드백 1-2: 표준가격/가격단위 0 방지 (`CheckPositive` 신규)
강사님은 "가격"만 0이 아니게 하라고 했지만, 표준가격단위(Peinh)도 최소 1은 되게 하는 게 맞다고 판단해서 함께 체크하기로 함.

```abap
validation CheckPositive on save { create; update; field Stprs, Peinh; }
```

> Validation 이름은 8/20~21에 정리해둔 네이밍룰 중 `CheckAmountPositive`(금액이 양수인지) 케이스에서 일부 따옴.

```abap
METHOD CheckPositive.
  READ ENTITIES OF zr_b07_mara IN LOCAL MODE
    ENTITY zr_b07_mara
    FIELDS ( Stprs Peinh )
    WITH CORRESPONDING #( keys )
    RESULT DATA(lt_mara).
  LOOP AT lt_mara INTO DATA(ls_mara).
    IF ls_mara-Stprs <= 0. "표준 가격은 0보다 커야 한다.
      APPEND VALUE #( %tky = ls_mara-%tky ) TO failed-zr_b07_mara.
      APPEND VALUE #( %tky = ls_mara-%tky
                      %element-Stprs = if_abap_behv=>mk-on
                      %msg = new_message( id = 'ZMSGE_B07'
                                          number = '023'
                                          v1 = 'Standard Price'
                                          severity = if_abap_behv_message=>severity-error ) )
          TO reported-zr_b07_mara.
    ENDIF.
    IF ls_mara-Peinh <= 0. " 가격 단위 역시 1, 2, ... 등 양수가 되어야 한다.
      APPEND VALUE #( %tky = ls_mara-%tky ) TO failed-zr_b07_mara.
      APPEND VALUE #( %tky = ls_mara-%tky
                      %element-Peinh = if_abap_behv=>mk-on
                      %msg = new_message( id = 'ZMSGE_B07'
                                          number = '023'
                                          v1 = 'Price Unit'
                                          severity = if_abap_behv_message=>severity-error ) )
          TO reported-zr_b07_mara.
    ENDIF.
  ENDLOOP.
ENDMETHOD.
```

> 메시지 [`023`](../../src/message-class.md#023): "&1 must be greater than 0."

다행히 Peinh가 정수 타입이라 0.99 같은 값은 입력 단계에서부터 막히는 것을 확인. 선언 추가 후 draft determine action Prepare에도 반영 잊지 않기:

```abap
draft determine action Prepare{
  validation CheckCreated;
  validation CheckInit;
  validation CheckMaterial;
  validation CheckSLoc;
  validation CheckBklas;
  validation CheckPositive;
}
```

### [01] 자재관리 — 피드백 1-3: 자재코드 서치헬프 제거
```abap
// 서치헬프 => 는 피드백에 의해 주석 처리 (삭제)
// @Consumption.valueHelpDefinition: [{ entity: { name: 'ZI_B07_MATNR_F4', element: 'Matnr' } }]
Matnr,
```
이 annotation을 지우면 List Report 검색바에서도 F4 도움말이 없어지지만, FS 요구사항(3.4 "검색조건: 자재타입과 자재는 기본적으로 보이게 설정")은 selectionField 여부에 관한 것이지 valueHelp 여부가 아니므로 검색 자체(텍스트 입력 필터링)에는 영향이 없다고 판단하여, 아예 없애는 방향으로 피드백을 반영함. 나중에 selectionField에는 F4를 적용하되 List/Object Page(특히 생성 시)에는 적용하지 않는 방법을 찾으면 다시 시도해볼 수 있음.

피드백 1-4는 필수 사항이 아니라 우선 패스.
