## 진행 내용

### FS 개요
공급업체와 자재를 플랜트별로 조합해 구매가격/최대구매수량/예정배송일수/유효종료일을 관리하는 구매정보 레코드(Purchasing Info Record) 기능. RAP Managed Scenario 기반 Create/Update/Delete/Draft, Fiori Elements UI, OData V4 서비스 노출까지가 목표.

01~04와 다른 점: **헤더(EINA)까지도 Interface View로 한 겹 감싼다.** 02번 FI계정관리에서 `ZI_B07_SKA1TEXT`(Text Interface)를 Root가 참조했던 패턴과 결은 같지만, 05번은 헤더/아이템 둘 다 Interface를 거쳐서 Root로 올라가는 구조라 한 단계가 더 붙는다.

```
ZTB07EINA (헤더 테이블)  →  ZI_B07_EINA (헤더 Interface View)  ┐
                                                                ├→ ZR_B07_EINA (Root BO View, Composition으로 결합)
ZTB07EINE (아이템 테이블) →  ZI_B07_EINE (아이템 Interface View) ┘

ZR_B07_EINA / ZI_B07_EINE  →  ZC_B07_EINA / ZC_B07_EINE (Projection View)
```

### DB Table 생성 — [`ZTB07EINA`](../../reference/05_purchase-info.md), [`ZTB07EINE`](../../reference/05_purchase-info.md)

#### 헷갈리는 필드 정리
`bprme`(발주 단위)는 실제 발주할 때 쓰는 단위(예: EA/KG/BOX). `peinh`(가격 단위)는 `netpr`이 몇 개의 `bprme`당 매겨진 가격인지 나타내는 배수(예: peinh=10 → "10개당" 가격). `netpr`(구매가격)은 `peinh` 단위당 가격의 총액이라, 실제 단가는 `netpr ÷ peinh` = `bprme` 1개당 가격이 된다. `waers`는 `netpr`이 표시된 통화. `bstma`(최대구매수량)는 이 구매정보 조건으로 한 번에 발주 가능한 최대 수량인데, 이 수량의 단위가 `bprme`(발주단위)를 따른다는 전제가 깔려 있다 — 자재 기본단위(헤더의 `meins`)가 아니라 발주단위 기준으로 관리하는 설계다. 발주단위로 가격을 매기고 발주단위로 최대수량도 관리한다는 점에서 일관된 논리이긴 하나, 팀이 의도한 설계가 맞는지는 한 번 더 확인이 필요해 보임.

#### 2~4. `ZI_B07_EINE`(아이템 Interface) ↔ `ZR_B07_EINA`(Root) 순환 생성
ADT에서 `ZI_B07_EINE`는 **Define View Entity With To Parent Association** 템플릿으로 생성(까먹으면 Templates에서 다시 바꿔야 함). 다만 parent(`ZR_B07_EINA`)가 아직 없는 상태라 일단 저장만 해두고, `ZR_B07_EINA`를 **Define Root View Entity**로 먼저 만들어(association 부분은 주석 처리) Active. 그 다음 `ZI_B07_EINE`로 돌아와 `association to parent`를 마저 정의.

생성자/생성시간/수정자/수정시간 Semantics Annotation을 처음엔 빠뜨렸다가(단순 필드로만 매핑) 뒤늦게 확인해서 추가한 최종본. [코드 보기](https://github.com/grace7410-byte/sap-kdt-project/blob/main/src/05_purchase-info/cds/ZI_B07_EINE.ddls.asddls)
```abap
@AbapCatalog.viewEnhancementCategory: [#NONE]
@AccessControl.authorizationCheck: #NOT_REQUIRED
@EndUserText.label: '구매정보레코드 아이템 Interface View'
@Metadata.ignorePropagatedAnnotations: true
define view entity zi_b07_eine as select from ztb07eine
association to parent zr_b07_eina as _Eina
    on $projection.InfUuid = _Eina.InfUuid
{
    key inf_uuid as InfUuid,
    key werks as Werks,
    @Semantics.amount.currencyCode : 'Waers'
    netpr as Netpr,
    peinh as Peinh,
    bprme as Bprme,
    waers as Waers,
    @Semantics.quantity.unitOfMeasure : 'Bprme'
    bstma as Bstma,
    prdat as Prdat,
    aplfz as Aplfz,
    @Semantics.user.createdBy: true
    created_by     as CreatedBy,
    @Semantics.systemDateTime.createdAt: true
    creation_at    as CreationAt,
    @Semantics.user.lastChangedBy: true
    changed_by     as ChangedBy,
    @Semantics.systemDateTime.lastChangedAt: true
    changed_at     as ChangedAt,
    @Semantics.systemDateTime.localInstanceLastChangedAt: true
    loc_changed_at as LocChangedAt,
    _Eina
}
```

#### 5. `ZR_B07_EINA` — Root View 최종
`zi_b07_eina`를 select 대상으로, `_Eine`를 composition으로 연결. 여기에 공급업체(`_Lfa1`)/자재(`_Mara`) association을 추가해서 필드 순서(공급업체/자재/구매정보번호), 텍스트(공급업체명/자재명)까지 끌어옴. FS가 "레코드유형명"도 끌어오라고 했는데 마침 레코드 유형은 `I_Domain*`으로 텍스트를 끌어올 수 있어서 그 방향으로 하려고 했으나, 오늘은 여기까지만 정리하고 실제 association 코드는 다음에 마저 작성하기로 함(TODO로 남겨둠).

[코드 보기](https://github.com/grace7410-byte/sap-kdt-project/blob/main/src/05_purchase-info/cds/ZR_B07_EINA.ddls.asddls)
```abap
@AccessControl.authorizationCheck: #NOT_REQUIRED
@EndUserText.label: '구매정보레코드 헤더 Root BO View'
@Metadata.ignorePropagatedAnnotations: true
define root view entity zr_b07_eina
  as select from zi_b07_eina
  composition[0..*]  of zi_b07_eine as _Eine

  association[0..1] to ZR_B07_LFA1 as _Lfa1
      on  $projection.LifUuid = _Lfa1.LifUuid

  association[0..1] to zr_b07_mara as _Mara
      on  $projection.MatUuid = _Mara.MatUuid
{
  key InfUuid,
      Infnr,
      Esokz,
      // TODO: Esotx(레코드유형명) — I_Domain* 기반 예정, 코드 미확정

      /* 공급업체 코드 및 공급업체명 */
      LifUuid,
      _Lfa1.Lifnr,
      _Lfa1.Name1 as Liftx,

      /* 자재코드 및 자재명 */
      MatUuid,
      _Mara.Matnr,
      _Mara._MaraText[1: Spras = $session.system_language].Maktx,

      Ekorg,
      Ekgrp,
      Meins,
      Loekz,
      @Semantics.user.createdBy: true
      CreatedBy,
      @Semantics.systemDateTime.createdAt: true
      CreationAt,
      @Semantics.user.lastChangedBy: true
      ChangedBy,
      @Semantics.systemDateTime.lastChangedAt: true
      ChangedAt,
      @Semantics.systemDateTime.localInstanceLastChangedAt: true
      LocChangedAt,
      _Eine // Make association public
}
```

> Esotx가 아직 Root에 없는 상태에서 Projection(`ZC_B07_EINA`)이 이미 Esotx를 참조하고 있어서, 다음 작업일에 Esotx association부터 마저 채워야 Projection이 정상 활성화됨.

#### 6. `ZC_B07_EINA` / `ZC_B07_EINE` — Projection View
Parent는 `provider contract transactional_query` + `root` 키워드로, Child는 `redirected to parent`, Parent는 다시 `redirected to composition child`로 서로 연결.

FS 요구사항 3.2~3.4 반영: (1) 필드 순서 공급업체(공급업체명)/자재(자재명)/구매정보번호 — MDE에서 position으로 마무리 예정, (2) Sort는 구매정보번호 → 자재 → 공급업체 순, (3) 검색조건은 공급업체/자재 2개. 서치헬프는 우선 보류.

[코드 보기: ZC_B07_EINA](https://github.com/grace7410-byte/sap-kdt-project/blob/main/src/05_purchase-info/cds/ZC_B07_EINA.ddls.asddls)
