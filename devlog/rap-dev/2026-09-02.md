### Eclipse Gateway 에러 로그 정리 중 Ekgrp F4 문제의 진짜 원인 발견
Eclipse에 들어가자마자 쌓여있던 Gateway 에러 로그를 정리하다가, 가장 최근 에러 전문을 확인해 원인을 찾음.

🐛 원인: `T024`의 `Ldest`(출력장치/프린터 지정 필드)에는 SAP 표준 도메인 상 `SPDEV`라는 Conversion Exit(프린터 이름 표시 변환 로직)이 걸려있는데, RAP V4 OData는 이 Conversion Exit을 지원하지 않아서 `Ldest` 필드가 노출되는 순간 서비스 자체가 내부 에러가 났던 것. 지난번 Warning 목록에 있던 "Search help assignment for field 'Ldest' is not inherited" 경고가 이미 힌트였는데 그때는 무관한 걸로 넘겼었음.

✅ 해결: `ZI_B07_EKGRP_F4`에서 `Ldest` 필드 제거. 겸사겸사 드롭다운 옵션(`@ObjectModel.resultSet.sizeCategory: #XS`)도 다시 제거(이메일/내선전화 등 여러 필드를 다 띄우는 게 의미가 있어서), `Ekgrp`/`Eknam`에 검색조건 어노테이션 추가.

관련 오브젝트: [`ZI_B07_EKGRP_F4`](../../reference/00_common-searchhelp.md) · [코드 보기](../../src/00_common-searchhelp/cds/ZI_B07_EKGRP_F4.ddls.asddls)

### 캐시 문제 — 뷰 삭제 후 재생성으로 해결
위 수정을 다 마쳤는데도 변경된 F4 Help가 계속 적용이 안 됨. 캐시 문제로 추정해 `ZI_B07_EKGRP_F4` 뷰 자체를 지우기로 함 — 지우려니 03(벤더)/05(구매정보레코드) 등 3곳에서 참조 중이라고 해서, 참조하는 쪽부터 먼저 주석 처리하고 뷰 안의 내용도 다 비운 뒤에야 DELETE가 됨. 그 후 다시 생성하니 그제서야 변경사항이 반영됨.

### Vendor/Material 필수값 오류 — 진짜 원인을 찾기까지 (3차 시도)
어제부터 이어진 `Field Material is required and cannot be empty.` / `Field Vendor is required and cannot be empty.` 문제를 오늘 붙잡고 해결.

**1차 시도(원인 예상) — `SetVendorMaterialUuid` Determination 신규 작성.** 화면의 `Lifnr`/`Matnr` 입력창이 실제 저장 필드가 아니라 Association에서 끌어오는 표시용 필드(`_Lfa1.Lifnr`, `_Mara.Matnr`)라서, 사용자가 입력한 값을 UUID로 변환하는 Determination이 필요하다고 판단해 작성. 실행 순서(UUID 채움 → 기본값 채움 → 채번)까지 신경써서 BDEF에 배치했으나, 이것만으로는 문제가 해결되지 않음.

**2차 시도(원인 예상) — `@ObjectModel.foreignKey.association` 어노테이션.** `Lifnr`/`Matnr`에 이 어노테이션을 붙이면 Value Help로 값을 고를 때 Association의 ON조건을 거꾸로 타고 올라가 FK 필드(LifUuid/MatUuid)에 자동으로 채워준다는 걸 알게 되어, 어제 만든 `SetVendorMaterialUuid`를 통째로 삭제(클래스 메소드/BDEF 모두)하고 이 어노테이션으로 대체 시도. 안 됨 — 다시 원상복구(`SetVendorMaterialUuid` 복원, 어노테이션 제거).

**3차 시도(진짜 원인, 적중) — `CheckRequired`가 문제였음.** 이 메시지가 정확히 어느 로직에서 나오는지부터 확인했어야 했는데, 그동안 이 생각을 못 하고 있었음. 확인해보니 `CheckRequired`가 화면 입력 필드(`Lifnr`/`Matnr`)가 아니라 아직 채워지지 않은 백엔드 필드(`LifUuid`/`MatUuid`)를 검사하고 있었음 — 값을 입력해도 UUID는 여전히 비어있으니 항상 필수값 에러가 먼저 터진 것.

✅ 해결: `CheckRequired`의 검사 대상을 `LifUuid`/`MatUuid`에서 `Lifnr`/`Matnr`로 변경. 공급업체부터 고쳤더니 Vendor 오류가 사라지고 Material 오류만 남아서, 동일하게 자재도 수정.

관련 오브젝트: [`zbp_r_b07_eina.clas.abap`](../../reference/05_purchase-info.md) · [코드 보기](../../src/05_purchase-info/bimp/zbp_r_b07_eina.clas.abap)
```abap
METHOD CheckRequired.
  READ ENTITIES OF zr_b07_eina IN LOCAL MODE
    ENTITY zr_b07_eina
*        FIELDS ( LifUuid MatUuid Meins )
*        WITH CORRESPONDING #( keys )
    ALL FIELDS WITH CORRESPONDING #( keys )
    RESULT DATA(lt_eina).

  LOOP AT lt_eina INTO DATA(ls_eina).
*      IF ls_eina-LifUuid IS INITIAL.
    IF ls_eina-Lifnr IS INITIAL.
      APPEND VALUE #( %tky = ls_eina-%tky ) TO failed-zr_b07_eina.
      APPEND VALUE #( %tky = ls_eina-%tky
                      %element-LifUuid = if_abap_behv=>mk-on
                      %msg = new_message( id = 'ZMSGE_B07'
                                          number = '015'
                                          v1 = 'Vendor'
                                          severity = if_abap_behv_message=>severity-error ) )
          TO reported-zr_b07_eina.
    ENDIF.

*      IF ls_eina-MatUuid IS INITIAL.
    IF ls_eina-Matnr IS INITIAL.
      APPEND VALUE #( %tky = ls_eina-%tky ) TO failed-zr_b07_eina.
      APPEND VALUE #( %tky = ls_eina-%tky
                      %element-MatUuid = if_abap_behv=>mk-on
                      %msg = new_message( id = 'ZMSGE_B07'
                                          number = '015'
                                          v1 = 'Material'
                                          severity = if_abap_behv_message=>severity-error ) )
          TO reported-zr_b07_eina.
    ENDIF.

    IF ls_eina-Meins IS INITIAL.
      APPEND VALUE #( %tky = ls_eina-%tky ) TO failed-zr_b07_eina.
      APPEND VALUE #( %tky = ls_eina-%tky
                      %element-Meins = if_abap_behv=>mk-on
                      %msg = new_message( id = 'ZMSGE_B07'
                                          number = '015'
                                          v1 = 'Base Unit'
                                          severity = if_abap_behv_message=>severity-error ) )
          TO reported-zr_b07_eina.
    ENDIF.
  ENDLOOP.
ENDMETHOD.
```

핵심 원인 요약: 수정 전(UUID 체크)에는 화면에 값을 입력해도 백엔드 UUID가 비어있어 `CheckRequired`의 필수값 에러가 최우선으로 발생했고, UI 프레임워크 특성상 상위 단계인 필수값 에러가 터지면 후속 단계(외래키/Value Help 존재 여부 검증)는 생략되거나 팝업 뒤로 묻혔음. 자연키(Lifnr/Matnr) 체크로 바꾸며 필수값 에러가 해소되니, 다음 검증 단계인 `Meins` 존재 여부 체크(값 없음 오류)가 정상적으로 동작하기 시작함.

### SetInfnrNumber 로직 단순화
이미 구성해둔 넘버레인지(`ZNRB07_INF`)를 그대로 사용하기로 해서, 연도(4자리)+뒤 6자리로 재가공하던 로직을 제거하고 `NUMBER_GET_NEXT` 채번 결과를 그대로 쓰도록 수정.

관련 오브젝트: [`zbp_r_b07_eina.clas.abap`](../../reference/05_purchase-info.md) · [코드 보기](../../src/05_purchase-info/bimp/zbp_r_b07_eina.clas.abap)
```abap
IF sy-subrc = 0.
*        DATA(lv_seq)   = substring( val = lv_number
*                            off = strlen( lv_number ) - 6 ).
*        DATA(lv_infnr) = |{ sy-datum(4) }{ lv_seq }|.
  APPEND VALUE #( %tky  = ls_eina-%tky
                   Infnr = lv_number ) TO lt_update.
```

### 테스트 진행 — 저장까지 확인됨
1번(오류 메시지 정비) 확인하려던 도중 얼떨결에 저장까지 완료됨. 알게 된 사실:
- 공급업체 입력 시(저장 이후로) 공급업체명/구매조직/구매그룹을 확인할 수 있음
- 자재 입력 시(저장 이후로) 자재명을 확인할 수 있음
- 아이템 없어도 저장됨
- `SetInfnrNumber` 채번 결과가 `5500000000` 형태로 잘 들어감 — 이전 로직(연도+뒤6자리)이 아니라 넘버레인지 결과 그대로 사용하는 게 확인됨

### 1-1 재확인 — 단위 메시지 정상화
저장된 버전에서 Edit → 다시 테스트해보니, 아까와 달리 단위(Meins) 오류 메시지가 "값이 존재하지 않는다"로 제대로 표시됨. `CheckRequired` 수정 덕분에 후속 검증 단계까지 정상적으로 도달하게 된 것으로 확인.

### 1-2 재확인 — 새로운 문제 발견
이번엔 오류 자체가 안 뜨고 그냥 저장이 되어버림. 존재하지 않는 값(`LOL2O2L`)을 공급업체에 입력했더니, 공급업체 코드는 빈 값으로 들어가고 자재는 `001`이 자동으로 들어가는 현상 확인.

🐛 원인: `SetVendorMaterialUuid`가 입력한 Lifnr/Matnr로 마스터 DB를 조회했을 때 못 찾아도(`sy-subrc <> 0`) UUID에 아무 값도 안 채우고 그냥 넘어가고, 이후 `CheckDuplicate` 등에서 UUID가 없는 상태로 저장을 통과시켜버림. 수정이 필요한 메서드 2개를 확인:
- `SetVendorMaterialUuid`: 마스터 DB에 없는 값이면 UUID를 채우는 대신 에러 메시지(reported)를 뱉고 실패(failed) 처리해야 함
- `CheckRequired`: 에러 시 하이라이트되는 필드를 `%element-LifUuid`/`%element-MatUuid`가 아니라 화면 입력 필드인 `%element-Lifnr`/`%element-Matnr`로 바꿔야 함

→ 오늘은 코드 반영까지는 못 함, 다음 작업일 처리 예정.

### 기타 발견한 것
처음 Create 버튼을 누르면 구매정보번호(Infnr) 입력창이 뜨는데, 직접 입력이 되는 것을 확인 — 자동채번 필드인데 편집 가능한 상태로 남아있어서 이상함. Infnr을 직접 입력 못 하게(readonly) 처리해야 할 것 같음 — 아직 미착수.
