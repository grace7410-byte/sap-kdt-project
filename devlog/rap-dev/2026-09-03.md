## 진행 내용

### 최종 산출물 안내 확인 — 개발 방향 조정
어제 "내일 공지가 나온다"고 예상했던 그 공지가 실제로 올라옴. 개인 포트폴리오·최종평가·수료식 발표 일정 안내였고, 특히 포트폴리오 구성 항목 중 "① 회사 개요 → ② AS-IS/TO-BE 비교 → ③ RAP 설계 → ④ RAP 구현(Classic ABAP과 RAP의 구현 방식 비교)"가 명시되어 있어, 점수 반영 포인트가 "Classic ABAP 프로그램과 (락/드래프트 등 RAP 고유 기능이 적용된) RAP 프로그램을 실제로 만들어 비교/분석하는 것"에 있다고 판단함.

이 판단에 따라 오늘부터 우선순위를 다음과 같이 재조정:
- 05(구매정보레코드)는 1차 개발 및 테스트가 이미 끝났으므로 마무리 처리.
- 06(구매오더)부터는 RAP 버전과 Classic ABAP 버전을 각각 만들어 AS-IS → TO-BE 비교 근거로 삼기로 함. 단, RAP 버전(`ZR_B07_EKKO` 등)은 별도로 진행 중인 기존 프로젝트에서 계속 진행하고, **이 저장소(이 프로젝트)에서는 Classic ABAP 버전(`SAPMZB07EKKO`)만** 다루기로 함.

### 신규 프로젝트 생성 — MM0004→EKKO 마이그레이션 분석
1기 프로젝트에서 만들었던 Classic ABAP Module Pool 프로그램 `SAPMZB1MM0004`(TOP/C01/O01/I01/F01 + 화면 구성)를 이번 06 구매오더 FS(`RAP_06_구매오더_FS_v10`) 기준으로 재작성하기 위한 신규 프로젝트를 생성함. 작업 전제를 다음과 같이 정리:
- `SAPMZB1MM0004 → SAPMZB07EKKO`는 RAP 전환이 아니라 **Classic ABAP → Classic ABAP 재작성(이관)**.
- 기존 `SAPMZB1MM0004`가 쓰던 테이블/함수모듈/메시지 클래스는 재사용하지 않음. 테이블은 FS(`06_구매오더_FS_v10`) 기준 신규 테이블(`ZTB07EKKO`/`ZTB07EKPO`)을 쓰고, 함수모듈은 전부 새로 생성, 메시지는 `ZMSGE_B07`에 신규 채번.
- 화면 흐름/로직 단위는 나중 RAP 버전과의 비교가 수월하도록, 06 FS의 구매오더 프로세스(생성 → GR → IV, `ELIKZ`/`EREKZ` 플래그 등) 단위에 맞춰 잘게 나눠서 구현.

**설계 원칙 — 물리 테이블과 Draft 테이블의 분리.** 이번 설계의 핵심은 Classic ABAP 프로그램과 RAP이 액티브 테이블(`ztb07ekko`/`ztb07ekpo`)을 공통으로 쓰되, Draft 테이블은 Classic 쪽에서 아예 쓰지 않는다는 것. 그래서 액티브 테이블엔 Draft 관련 필드를 넣지 않고, UUID PK + client + 순수 업무 필드 구성만 유지함. Draft 활성 레코드를 저장하는 실제 Draft 테이블(RAP이 Behavior Definition 활성화 시 자동 생성)은 이 물리 테이블과 완전히 분리해서 별도로 뜨게 둠.

이렇게 나눈 이유는 `ztb07ekko`/`ztb07ekpo`를 나중에 Classic ABAP 프로그램(배치, 리포트 등)에서도 직접 SELECT/INSERT 하게 될 걸 전제하고 있기 때문 — RAP 전용이었다면 Draft까지 고려한 필드를 물리 테이블에 넣어도 됐겠지만, 그러면 Classic 쪽 로직이 "지금 이 레코드가 활성인지 Draft인지"를 신경 써야 하는 상황이 생김. 그래서 원칙을 세움: **물리 테이블은 액티브 데이터만 갖고, Draft는 RAP BO 레이어(CDS Root View + Behavior Definition)에서만 선언·관리한다.**

CDS 단으로 옮기면: `ZI_B07_EKKO`/`ZI_B07_EKPO`(Interface View)는 물리 테이블을 그대로 Select — 여기까진 Classic 프로그램이 봐도 되는 범위. `ZR_B07_EKKO`(Root View Entity)에서만 `with draft;`를 선언해 Draft 테이블 생성·관리를 시작. Classic 프로그램은 Interface View나 물리 테이블만 참조하고, Root View/Draft 테이블 쪽은 알 필요도 알아서도 안 되는 영역으로 선을 그음.

### 채번 오브젝트 설정 — ZNRB07_EBE
`EBELN`(구매오더번호) 채번용 넘버레인지 `ZNRB07_EBE`를 4500000000~4599999999 구간으로 생성. FS에 "41로 시작하는 건 외부용, 내부 채번은 45번대"로 명시된 건 이번이 처음(기존 05까지의 넘버레인지는 이런 구분이 없었음).

### SAPMZB07EKKO 메인 프로그램 + TOP Include 작성
1기 `SAPMZB1MM0004`(TOP/C01/O01/I01/F01 + 화면) 구조를 계승해, `SAPMZB07EKKO` 메인 프로그램에 동일한 5개 Include(`ZB07EKKO_TOP`/`_C01`/`_O01`/`_I01`/`_F01`) 골격을 잡음. GUI Text(T100~T300)·메시지 클래스(`ZMSGE_B07`, 신규 채번, 1기 `ZMCB1` 재사용 안 함) 배치도 주석으로 미리 표시해둠.

이어서 TOP Include(전역 데이터 선언)까지 작성 완료. 헤더(`ty_head`)/아이템(`ty_item`) 구조는 각각 `ZTB07EKKO`/`ZTB07EKPO` 필드를 그대로 반영하되, `Lifnr`/`Matnr`/`Infnr`처럼 DB엔 없고 화면입력/검색용으로만 쓰는 보조필드는 별도 표시해둠. 그 외 공급업체 마스터(`gs_vend`) 조회용 구조, 옵션가(구매정보레코드 기준 단가, `ZTB07EINA`+`ZTB07EINE` JOIN 결과 — 1기는 CDS로 실시간 계산했는데 이번엔 이 방식으로 재설계, 방향 확인 필요), BOM 조성비 조회용 구조(`gs_bom`/`gs_bom_all`), 아이템/벤더/옵션가/BOM차트/헤더목록 등 화면별 ALV·Chart Engine 컨트롤 변수까지 선언 완료.

### BOM 관련 검토 — 원유 기준 → 완제품(휴대폰) 기준 전환 필요성 확인
1기 프로젝트에서는 원유(Crude Oil) 조성비 기준 BOM이었는데, 이번 06은 완제품(휴대폰) 대비 부품 구성비로 주제가 바뀐다는 걸 뒤늦게 인지함. 기존 "역BOM 구조"(원유 하나를 여러 완제품으로 정제하는 방향)에서 이번엔 "정상 BOM 구조"(완제품 하나가 여러 부품으로 구성되는 방향)로 성격 자체가 달라지는 것이라, 제품 설계 및 데이터 작성을 처음부터 다시 해야 할 것으로 판단됨. `ZTB07BOM` 테이블(`STLNR`/`STLKN`/`BOMVE`/`COMP_UUID`/`FMENG`/`MEINS` 등 헤더-노드 구조)은 원유든 완제품이든 동일한 구조로 표현 가능해 구조 자체는 유지하되, 기준이 되는 완제품(휴대폰 모델) 코드/제품 라인업 확정과 그에 맞는 데이터 작성이 선행되어야 함. 차기 BOM 설계는 별도 검토 중.
