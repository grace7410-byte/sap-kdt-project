## 진행 내용

### BOM 라인업 설계 — 원유(1기) → S-Mobile(2기) 전환
FS 원문의 취급 품목 4단(완제품 Set / 반제품 / 부품·소모품 / 포장재) 구조를 브랜드만 "S-Mobile"로 바꿔서 **판매상품 → 반제품 → 원자재(부품)** 3계층으로 정리함.
- 1단(판매상품, FERT/HAWA): S-Mobile Fold(폴더블) / Flip(플립형) / Standard(일반형) — 1기 "원유 3종 중 택1" 구조를 계승.
- 2단(반제품, HALB): 본체 Unassembled(모델별로 갈라짐) / PCB Assembly(공통).
- 3단(원자재/부품, ROH+VERP): USB C-Type 케이블, 심 트레이, 제품 외장 박스, 설명서, 보호 필름, 완충재, 스티커, 포장 테이프 — FS 원문 그대로 계승.

1기(원유)는 "1개 투입 → N개 산출(연산품 6종) 비율"을 보여주는 구조였는데, S-Mobile은 방향이 반대인 "N개 투입(부품/반제품) → 1개 산출(완제품)"을 조립하는 정방향 BOM이라, 비율 그래프도 "이 모델 1대에 부품이 몇 개 들어가는가"를 보여주는 소요량 그래프로 바뀌어야 한다는 점을 확인함.

표준 자재관리는 자재 하나(MATNR)에 대해 플랜트마다 별도 View(MARC 등)를 갖는 구조지만, 현재 `ZTB07MARA`는 이를 단순화해 자재 1건당 Werks/Lgort를 1개만 갖는 구조라서, 이 프로젝트 범위에서는 대표 플랜트 1개(K220)만 골라 확정함.

### 언어 F4 Value Help — 여러 차례 시행착오 끝에 최종 해결 (`ZI_B07_SPRAS_F4`)
15개 자재를 하나씩 입력하던 중, 언어 F4 Value Help(Create 팝업)에서 데이터가 하나도 안 뜨는 문제 발견.

🐛 원인: 베이스 테이블이 표준 언어 마스터(`T002`)가 아니라 커스텀 텍스트 테이블(`ztb07mara_t`)이라, 이미 자재명이 등록된 언어만 보여주는 구조였음. 자재명이 아직 없는 신규 생성 시점엔 조회 결과가 0건이 되는 게 당연한 것이었음.

**1차 수정 — base table을 `ztb07mara_t` → `t002`(+`t002t`)로 교체.** 항상 전체 언어 목록이 뜨도록 수정했으나, 이번엔 `Language`(자기 자신 `spras`를 그대로 노출)가 세션 언어에 따라 고정되어 Language Key가 너무 많이 뜨는 문제 발생.

**2차 수정 — `where` 절로 `spras = 'E' OR '3'` 필터링.** FS에서 EN/KO만 쓰라고 했으니 하드코딩 없이는 두 개만 띄우는 게 불가능하다고 판단해 필터 추가. 이번엔 또 다른 오류 발견 — 예전에 고쳤던 것 같은 문제가 재발함. `T002T`를 직접 조회해본 결과, `SPRAS`(언어 자체)와 `SPRSL`(그 언어명을 어떤 언어로 표기할지)의 관계가 "SPRAS가 가리키는 언어의 이름을, SPRSL 언어로 번역해서 보여준다"는 구조라는 걸 재확인 — 즉 처음 가정과 반대로 읽어야 하는 구조였음.

**3차 수정 — `T002T` 단독 조회로 역할 반대 적용.** `T002`의 역할이 퇴색되어 `T002T`만으로 재작성. `where spras = $session.system_language and (sprsl = 'E' or sprsl = '3')`로 필터링. 잘 나오는 것 확인했으나, 다시 만들려는 순간 `EN(English)/KO(Korean)`이 나와야 할 자리에 `KO(Korean)/KO(Korean)`으로 중복 표시되는 문제 발견. Data Preview 자체는 정상이라 더 헷갈렸음.

🐛 진짜 원인: `Language` 컬럼에 `sprsl`(고정된 세션언어 `'E'`)을 그대로 매핑해서, 두 행 모두 `Language='E'`로 겹쳐 Value Help가 서로 다른 행을 구분하지 못했던 것. 애초에 "조인"이 필요했던 이유(3/E 대신 실제로 서로 다른 값인 EN/KO가 필요했기 때문)를 다시 떠올림.

✅ 최종 해결: `T002T`를 기준으로 `T002`를 다시 조인해 `laiso`(EN/KO — 실제 서로 다른 값)를 `Language`에 매핑하고, `LanguageKey`는 `sprsl`(3/E)로 key와 완전히 분리. 행마다 `Language`가 고유해져 정상 동작 확인.

관련 오브젝트: [`ZI_B07_SPRAS_F4`](../../src/00_common-searchhelp/cds/ZI_B07_SPRAS_F4.ddls.asddls)
```abap
define view entity zi_b07_spras_f4
  as select from t002t as a
    inner join   t002  as b on a.sprsl = b.spras
{
       @Search.defaultSearchElement: true
       @UI.hidden: true
  key  a.sprsl as LanguageKey, -- '3', 'E'
       @UI.hidden: true
       a.spras,
       @UI.textArrangement: #TEXT_LAST
       @ObjectModel.text.element: ['LanguageName']
       b.laiso as Language,
       @Semantics.text: true
       @Search.defaultSearchElement: true
       a.sptxt as LanguageName -- 'Korean', 'English'
}
where
       a.spras = $session.system_language
  and(
       a.sprsl = 'E'
    or a.sprsl = '3'
  )
```

15개 데이터를 모두 넣고 나니, FS 1.1 원문 기준으로 S-Mobile이 "부품·반제품을 외부 공급업체로부터 조달해 완성된 Set 상품으로 구성·판매"하는 기업임이 재확인됨. 한 줄 요약: **S-Mobile은 OEM 제조사가 아니라 반제품·부품을 조달해 완제품으로 조립·패키징해서 판매하는 유통/조립 전문 기업**(FS 원문 표현 "유통 전문 기업").

### `ZTB07BOM` 테이블 확정 — head_uuid안 vs STKO/STPO안 vs 실제 소스 확인
BOM 구성을 위해 처음엔 `head_uuid` 컬럼 추가안, 그다음 STKO/STPO 헤더+아이템 2단 구조안을 검토했으나, 1기 `SAPMZB1MM0004` F01(`get_chart_data`/`get_chart_data_all`)의 실제 소스를 직접 읽고 검증한 결과 둘 다 실제 구조와 달랐음을 확인함. 실제 1기 로직은 `BOMVE`(계절, 월별 실시간 산출)와 `FMENG` 부호(+/-)로 기준재료/산출물을 구분하는 완전 평면(flat) 테이블이었음.

이에 따라 3가지 결정사항 정리:
1. 플래그 컬럼 대신 `FMENG` 음수트릭 유지(완제품 행만 음수, 부품 행은 양수).
2. 계절(`BOMVE`) 컬럼 제거 — S-Mobile은 계절성 상품이 아님.
3. 3종 비교 대상 = 3개 모델(Fold/Flip/Standard).

`ZTB07BOM`을 위해 `zeb07stlnr`(데이터엘리먼트, 도메인 `zdb07stlnr` char 10) 신규 생성. 실제 ADT 코드 상에서는 필드별 주석이 불가능한 구조라, Git 기록용으로만 상단 대신 각 필드 우측에 설명을 붙임.

관련 오브젝트: [`ZTB07BOM`](../../src/06_purchase-order/tables/ZTB07BOM.tabl.asddls)
```abap
@EndUserText.label : 'BOM (부품구성) 마스터'
@AbapCatalog.enhancement.category : #NOT_EXTENSIBLE
@AbapCatalog.tableCategory : #TRANSPARENT
@AbapCatalog.deliveryClass : #A
@AbapCatalog.dataMaintenance : #ALLOWED
define table ztb07bom {
  key client   : abap.clnt not null;
  key bom_uuid : abap.raw(16) not null;
  stlnr        : zeb07matnr not null;      " 그룹ID (완제품 모델코드로 사용, 예: 'SM-FOLD')
  stlkn        : abap.numc(4) not null;    " 그룹 내 일련번호 10/20/30...
  comp_uuid    : abap.raw(16) not null;    " 자재 UUID → ZTB07MARA (완제품 자신도 여기 들어감)
  fmeng        : abap.dec(13,3);           " 수량 — 완제품 행만 음수, 부품 행은 양수 (1기 트릭 유지)
  meins        : meins;
  loekz        : zeb07del;
  include zsb07timestamp_v2;
}
```

### 구매오더 유형(BSART) 표시값 신규 생성
NB 옆에 "표준 구매오더" 텍스트가 안 뜨는 문제 확인 — `bsart : bsart;`로 잡아뒀던 표준 도메인/데이터엘리먼트 `BSART`에는 애초에 설명 텍스트(Fixed Value)가 없었음. 신규 도메인 `zdb07bsart`(Fixed Value 'NB'='표준 구매오더') + 데이터엘리먼트 `zeb07bsart` 생성 후 테이블 필드 타입 교체, 정상 표시 확인.

관련 오브젝트: [`ZTB07EKKO`](../../src/06_purchase-order/tables/ZTB07EKKO.tabl.asddls) (`bsart : bsart;` → `bsart : zeb07bsart;`)

이어서 05(구매정보레코드)의 `ESOKZ`(외주임가공 등 구분)가 구매오더의 `BSART`로 넘어오는지 궁금해 확인함 — **표준 SAP에서 `BSART`와 `ESOKZ`를 강제 연결하는 체크 테이블은 없고**, 실제 외주가공 여부를 결정하는 건 아이템 품목범주(`EPSTP`/표준 `PSTYP`, `3`=외주)이며 `ESOKZ`(`1`=Subcontracting)는 그 아이템의 정보레코드 F4를 외주용으로만 필터링할 때 쓰인다는 것 확인. `BSART`는 이 흐름에 관여하지 않음(PO 전체 문서유형은 그대로 `NB`). EKPO에 이미 `EPSTP` 필드가 있으니, 외주가공 시나리오가 필요해지면 `BSART`가 아니라 `EPSTP`+`ESOKZ` 조합으로 처리하는 게 표준에 맞음 — 다만 S-Mobile이 조립/유통 전문 기업이라는 오늘 확인한 성격상 이 시나리오 자체가 이 프로젝트 범위에 필요한지는 별개 문제로 남겨둠.

### 101번 스크린 O01/I01/F01 마무리 + 실행 확인
`init_alv_0101`을 스텁에서 실데이터 조회 로직으로 교체, `set_fcat_vend`/`get_vendor_all_data`(F01) 신규 작성. `get_vendor_all_data`는 1기와 달리 조인 없이 `ZTB07LFA1` 단건 조회 → `AKONT` 기준 `ZTB07SKA1` 조회(SELECT+LOOP+READ 2단계)로 `GLACT`를 채우는 구조로 작성. 다시 액티브시켜 확인해보니 우상단 벤더 스크린 ALV에 데이터가 정상적으로 들어옴을 확인.

### 102번 F01 작성 (`get_vendor_data`/`get_domain_text`)
102번 서브스크린 전환/130번 팝업에서 공용으로 쓰는 `get_vendor_data`와, 도메인 Fixed Value → 설명 텍스트 조회 공통 유틸 `get_domain_text` 작성. `get_vendor_data`에서 `GLACT`(계정타입) 도메인명이 `ZDB07GLACT`인지 표준 `GLACCOUNT_TYPE` 도메인인지 확인 필요 표시를 코드 주석(`★`)으로 남겨둠. 130번 팝업 화면이 완료되어야 실제 테스트가 가능한 상태.
