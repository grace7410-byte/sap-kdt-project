### gv 텍스트 변수 미표시 — 표준 도메인 사용으로 Fixed Value 없음
이전과 달리 ZD~~ 도메인을 더 이상 안 쓰고,
```
bukrs : bukrs;
ekorg : ekorg;
ekgrp : ekgrp;
```
이런 식으로 스탠다드를 사용하는 바람에 FV(Fixed Value)가 없음. 실제 출력 시 서치헬프도 스탠다드 테이블에 값이 들어가있는 회사코드만 서치헬프 뜨고, 구매조직이랑 그룹은 서치헬프 뜨지도 않음. 이제 `get_domain_text` 말고도 `get_cds_text` 존재.

```abap
*&---------------------------------------------------------------------*
*& Form get_domain_text (도메인 Fixed Value → 설명 텍스트 조회)
*&---------------------------------------------------------------------*
FORM get_domain_text USING    p_gv_domname TYPE any   " ZDB07### 도메인명
                              p_gv_value   TYPE any   " Fixed Value 코드값
                     CHANGING c_gv_text    TYPE any.  " 조회된 설명 텍스트
  DATA: lt_domain_value TYPE TABLE OF dd07v,
        ls_domain_value LIKE LINE OF lt_domain_value.
  CLEAR c_gv_text.

  CALL FUNCTION 'GET_DOMAIN_VALUES'
    EXPORTING
      domname         = p_gv_domname
    TABLES
      values_tab      = lt_domain_value
    EXCEPTIONS
      no_values_found = 1
      OTHERS          = 2.

  IF sy-subrc = 0.
    READ TABLE lt_domain_value INTO ls_domain_value
      WITH KEY domvalue_l = p_gv_value.

    IF sy-subrc = 0.
      c_gv_text = ls_domain_value-ddtext.
    ENDIF.
  ENDIF.
ENDFORM.
*&---------------------------------------------------------------------*
*& Form get_cds_text (CDS 서치헬프 뷰에서 코드→텍스트 동적 조회)
*&---------------------------------------------------------------------*
FORM get_cds_text USING    p_viewname TYPE any    " CDS 뷰 이름, 예: 'ZI_B07_BUKRS_F4'
                           p_keyfield TYPE any    " 키 필드명,   예: 'COMPANYCODE'
                           p_keyvalue TYPE any    " 키 값,       예: gs_head-bukrs
                           p_valfield TYPE any    " 조회할 필드명, 예: 'COMPANYCODENAME'
                  CHANGING c_value    TYPE any.   " 결과 담을 변수, 예: gv_bukrs

  DATA: lv_where TYPE string.
  CLEAR c_value.

  lv_where = |{ p_keyfield } = { cl_abap_dyn_prg=>quote( CONV #( p_keyvalue ) ) }|.

  TRY.
      SELECT SINGLE (p_valfield)
        FROM (p_viewname)
        INTO (c_value)
        WHERE (lv_where).
    CATCH cx_sy_dynamic_osql_error.
      CLEAR c_value.   " 뷰/필드명 오타 등 동적 SQL 오류 시 조용히 비움
  ENDTRY.
ENDFORM.
```

### display_alv 컴파일 오류 해결 — "USING 참조 파라미터를 수정하지 마라" (199줄)
어떤 FORM이 `USING` 파라미터(기본은 참조전달)를 폼 본문 안에서 직접 대입/변경하고 있다는 지적. `display_alv`의 `pt_fcat`이 진짜 문제였음.

```abap
FORM display_alv USING    ps_layout  TYPE lvc_s_layo
                          pt_uifunc  TYPE ui_functions
                          pt_fcat    TYPE lvc_t_fcat     " ← USING인데
                 CHANGING po_alv     TYPE REF TO cl_gui_alv_grid
                          pt_outtab  TYPE ANY TABLE.
  ...
  CALL METHOD po_alv->set_table_for_first_display
    EXPORTING ...
    CHANGING
      it_outtab        = pt_outtab
      it_fieldcatalog  = pt_fcat        " ← 199줄. SET_TABLE_FOR_FIRST_DISPLAY가
    ...                                   이 파라미터 내용을 실제로 채워넣어(수정해) 돌려줌
```

`SET_TABLE_FOR_FIRST_DISPLAY`의 `it_fieldcatalog`는 CHANGING 파라미터라 메서드가 내용을 직접 수정한다(필드카탈로그 자동보정). `pt_fcat`을 `USING`(참조전달이지만 "안 바꿀 것"이라는 의미)으로 선언해놓고 안에서 바꿔버리니 컴파일러가 지적한 것. `pt_fcat`을 `CHANGING`으로 옮기면 해결.

```abap
*&---------------------------------------------------------------------*
*& Form display_alv (ALV 최초 표시)
*&---------------------------------------------------------------------*
FORM display_alv USING    ps_layout  TYPE lvc_s_layo
                          pt_uifunc  TYPE ui_functions
                 CHANGING po_alv     TYPE REF TO cl_gui_alv_grid
                          pt_outtab  TYPE ANY TABLE
                          pt_fcat    TYPE lvc_t_fcat.

  CALL METHOD po_alv->set_table_for_first_display
    EXPORTING
      is_layout                     = ps_layout
      it_toolbar_excluding          = pt_uifunc
    CHANGING
      it_outtab                     = pt_outtab
      it_fieldcatalog               = pt_fcat
    EXCEPTIONS
      invalid_parameter_combination = 1
      program_error                 = 2
      too_many_lines                = 3
      OTHERS                        = 4.
ENDFORM.
```

```abap

                    CHANGING go_alv gt_item.

" 수정
PERFORM display_alv USING gs_layout gt_uifunc
                    CHANGING go_alv gt_item gt_fcat_item.
```

### get_cds_text 덤프 및 디버깅 히스토리
```abap
*&---------------------------------------------------------------------*
*& Form get_cds_text (CDS 서치헬프 뷰에서 코드→텍스트 동적 조회)
*&---------------------------------------------------------------------*
FORM get_cds_text USING    p_viewname TYPE any
                           p_keyfield TYPE any
                           p_keyvalue TYPE any
                           p_valfield TYPE any
                  CHANGING c_value    TYPE any.

  DATA: lv_where TYPE string.
  CLEAR c_value.

  lv_where = |{ p_keyfield } = { cl_abap_dyn_prg=>quote( CONV #( p_keyvalue ) ) }|.

  SELECT SINGLE (p_valfield)
    FROM (p_viewname)
    INTO (c_value)
    WHERE (lv_where).
ENDFORM.
```

🐛 문제
- `SAPSQL_PARSE_ERROR`(메시지 484)가 `C_VALUE`를 지목. 실제 실행 값(`lv_where = 'COMPANYCODE = 'K200''`, `p_viewname = 'ZI_B07_BUKRS_F4'`, `p_valfield = 'COMPANYCODENAME'`)은 전부 정상이었음.

디버깅 히스토리:
- 시도 1: 동적 FORM(`get_cds_text`)으로 `SELECT SINGLE (p_valfield) FROM (p_viewname) INTO (c_value) WHERE (lv_where)` + `TRY/CATCH cx_sy_dynamic_osql_error`로 감싸서 작성 → 실패: 텍스트(`gv_bukrs` 등)가 안 뜸. 덤프도 안 남음(원인: `CATCH`가 실제 에러를 조용히 삼켜버려서 뭐가 문제인지 안 보이는 상태).
- 시도 2: 대소문자 문제인가 의심 → 아님(ABAP Open SQL은 대소문자 구분 안 함)으로 확인. `CATCH` 빼고 `BREAK-POINT`로 `lv_where`/`sy-subrc` 직접 확인 제안 → 진행 안 됨: CDS 뷰 소스(`ZI_B07_BUKRS_F4` 등) 원문 확인 후 "K200/1000/001이 실제 SPRO 마스터데이터로 존재 안 할 수도 있다"는 가설.
- 시도 3: 실제 런타임 덤프 확보 → `SAPSQL_PARSE_ERROR`(메시지 484), `C_VALUE` 지목 → 1차 원인 진단(틀림): "`INTO (c_value)`에서 괄호는 이름이 동적일 때만 쓰는 거고, `c_value`는 실제 변수라 괄호 빼야 한다"고 판단 → `INTO (c_value)` → `INTO c_value`로 수정.
- 시도 4: 괄호 뺀 버전 재실행 → 실패: 여전히 같은 위치(375줄)에서 `CX_SY_DYNAMIC_OSQL_SEMANTICS` 재발생. "변수 C_VALUE는 `@`로 이스케이프해야 합니다" — Strict SQL 모드라 호스트 변수엔 `@` 필수라는 것 확인 → `INTO c_value` → `INTO @c_value`로 재수정.
- 시도 5: 동적 FORM 말고 뷰별로 정적 SELECT 3개 따로 쓰는 걸로 방향 전환. `get_cds_text` 폼 자체를 폐기하고, `set_init_user_data`에 `SELECT SINGLE ... FROM zi_b07_xxx_f4 WHERE ... INTO @gv_xxx` 3개를 직접 작성 → 성공: 스크린샷으로 `1000 Basic Purc`/`001 Einkäufer`/`K200 가상 기업 S-Mo` 전부 정상 표시 확인, 덤프 없음.

✅ 최종 결론 (내 판단)
- `K200`/`1000`/`001`은 실제로 `T001`/`T024E`/`T024`에 다 존재했음 — 정적 SELECT가 한 번에 성공한 게 그 증거이므로, 마스터데이터 부재는 원인이 아니었음.
- 다만 "동적 Open SQL 문법 두 가지(괄호/`@`)가 진짜 원인이었다"는 분석에는 동의하지 않음. `TRY/CATCH`로 감쌌던 첫 시도가 에러를 조용히 삼켜서 원인 파악을 늦춘 것이 컸고, 최종적으로는 동적 SQL 자체를 포기하고 정적 SELECT 3개로 바꾼 게 정답이었음 — 뷰가 3개뿐이라 범용화의 이점이 크지 않았고, 정적으로 가니 동적 SQL 특유의 문법 함정(괄호/`@`) 자체가 사라졌음.

### set_init_user_data 최종 확정 — CDS 서치헬프 뷰 3개 정적 SELECT
각각 CDS 뷰에서 조회하기로 함.

```abap
*&---------------------------------------------------------------------*
*& Form set_init_user_data (하드코딩 기본값 + CDS 서치헬프 뷰로 텍스트 조회)
*&---------------------------------------------------------------------*
FORM set_init_user_data.
  gs_head-bukrs = 'K200'.
  gs_head-ekorg = '1000'.
  gs_head-ekgrp = '001'.

  SELECT SINGLE companycodename
    FROM zi_b07_bukrs_f4
    WHERE companycode = @gs_head-bukrs
    INTO @gv_bukrs.

  SELECT SINGLE ekotx
    FROM zi_b07_ekorg_f4
    WHERE ekorg = @gs_head-ekorg
    INTO @gv_ekorg.

  SELECT SINGLE eknam
    FROM zi_b07_ekgrp_f4
    WHERE ekgrp = @gs_head-ekgrp
    INTO @gv_ekgrp.
ENDFORM.
```

덤프 안 남, 3개 텍스트까지 잘 나오는 거 확인.

✅ 해결
