### 130번 로직 구성 — 핫스팟 이벤트(C01 신규) + 관련 주석 해제
101번 벤더 ALV에서 벤더(LIFNR/NAME1) 핫스팟 클릭 시 130번 팝업을 띄우는 이벤트 핸들러를 신규로 작성(`ZB07EKKO_C01` 신규 생성).

관련 오브젝트: [`ZB07EKKO_C01`](../../src/06_purchase-order/prog/ZB07EKKO_C01.prog.abap) · [`ZB07EKKO_O01`](../../src/06_purchase-order/prog/ZB07EKKO_O01.prog.abap) · [`ZB07EKKO_I01`](../../src/06_purchase-order/prog/ZB07EKKO_I01.prog.abap)

```abap
*&---------------------------------------------------------------------*
*& Include          ZB07EKKO_C01
*&---------------------------------------------------------------------*
CLASS lcl_event_handler DEFINITION.
  PUBLIC SECTION.
    CLASS-METHODS:
      "[101번] 벤더 ALV에서 핫스팟(LIFNR/NAME1) 클릭 시 130번 팝업 호출
      on_hotspot_click FOR EVENT hotspot_click
        OF cl_gui_alv_grid IMPORTING e_row_id e_column_id.
ENDCLASS.
CLASS lcl_event_handler IMPLEMENTATION.
  METHOD on_hotspot_click.
    " 1. 핫스팟 대상 컬럼인지 확인 — 공급업체번호/공급업체명 컬럼만 반응
    CHECK e_column_id-fieldname = 'LIFNR' OR e_column_id-fieldname = 'NAME1'.
    " 2. 클릭된 행의 벤더(LIFNR)로 상세 조회
    READ TABLE gt_vend INTO DATA(ls_selected_vend) INDEX e_row_id-index.
    IF sy-subrc = 0.
      " 3. 팝업용 조회(pv_pop = 'X') — gs_vend에 벤더 상세 채움
      PERFORM get_vendor_data USING 'X' ls_selected_vend-lifnr.
      " 4. gs_vend가 정상적으로 채워졌으면 130번 팝업 호출
      IF gs_vend-lifnr IS NOT INITIAL.
        CALL SCREEN '0130' STARTING AT 50 5
                           ENDING   AT 135 25.
      ENDIF.
      " 5. 팝업에서 SEL_VEND로 선택한 벤더가 방금 클릭한 벤더와 같으면(=방금 선택됨)
      "    I01의 WHEN OTHERS는 gs_head-lifnr <> gv_before_lifnr일 때만 도니까,
      "    102번 서브스크린 전환이 즉시 반영되도록 PAI를 한 번 강제로 더 돌림
      IF gs_head-lifnr = gs_vend-lifnr.
        cl_gui_cfw=>set_new_ok_code( EXPORTING new_code = 'ENTER' ).
      ENDIF.
    ENDIF.
  ENDMETHOD.
ENDCLASS.
```

### 테스트 (1)

- 130번 화면: 기본 데이터 출력까지는 정상 확인. 비주얼 조정이 필요하고, 아직 입력 가능 상태로 남아있는 필드들을 전부 입력 불가로 처리해야 함(단, 텍스트 전용 필드까지 output-only로 만드는 것은 아님). 계정 타입(GLACT) 텍스트가 출력되지 않는 상태로 확인됨.
- 102번 등 기타 화면: 102번은 정상 출력 확인. 다만 130번에서 벤더를 선택했을 때 100번 헤더 필드까지 반영되도록 로직을 추가해야 함 — 데이터상으로는 선택한 벤더의 EKORG/EKGRP가 `P02`였지만, 실제 100번 화면에는 기존 하드코딩값(회사코드/구매조직/구매그룹 순서대로 K200/1000/001)이 그대로 표시됨. `GV_구매조직`/`GV_구매그룹` 변수가 하드코딩 값을 갖고 있어 신규 데이터로 갱신되지 않는 상태.

#### GLACT(계정 타입) 텍스트 미출력 원인 확인 및 해결

GLACT 도메인을 확인한 결과, F01 코드가 존재하지 않는 `'ZDB07GLACT'`를 도메인명으로 넘기고 있어 `GET_DOMAIN_VALUES`가 값을 찾지 못해 텍스트가 비어 있었던 것으로 확인됨. 어제(09-05) 구매조직/구매그룹 텍스트 문제와 동일한 유형(도메인 Fixed Value 부재)이었음.

해결 방식으로 (1) EKORG/EKGRP 때처럼 CDS 뷰 SELECT를 추가하는 방법과 (2) 그 CDS 뷰가 쓰던 표준 도메인 타입 `GLACCOUNT_TYPE`을 직접 쓰는 방법을 검토했고, 후자로 결정.

관련 오브젝트: [`ZB07EKKO_F01`](../../src/06_purchase-order/prog/ZB07EKKO_F01.prog.abap)

```abap
PERFORM get_domain_text USING 'GLACCOUNT_TYPE' gs_vend-glact CHANGING gv_glact.
```

✅ 해결
- GLACT(계정타입) 텍스트 미표시 문제 — 도메인명을 `'ZDB07GLACT'`(존재하지 않음)에서 `'GLACCOUNT_TYPE'`으로 수정.

🐛 문제 (미해결)
- 130번에서 벤더 선택 시 100번 헤더의 EKORG/EKGRP가 하드코딩 값(1000/001)에서 선택한 벤더의 실제 값(P02 등)으로 갱신되지 않는 문제 — 1기 로직 이식 방향만 확인했고, 오늘 코드 반영은 아직 안 됨.

또한 1기 F01의 `get_header_data`/`get_vendor_data`를 다시 확인한 결과, 정확히 이 상황을 위한 로직(BP별 구매조건 조회 후 `gs_head-ekorg/ekgrp/bukrs`까지 덮어쓰고 텍스트 재조회)이 이미 있었음. 2기는 벤더 마스터(`ZTB07LFA1`)에 EKORG/EKGRP가 이미 있고 별도 BUKRS 필드는 없으므로, 그 구조에 맞게 이식하면 되는 방향으로 확인.

### 시도 (Git) — abapGit 설치
코드와 GitHub 사이에 반영 텀이 계속 발생해 혼란스러워, 이전 Fiori 때처럼 GitHub에 바로 반영되는 구조를 만들고 싶었음.

- **호스트**: `bgissap1`(또는 IP `61.97.134.34`)
- **인스턴스 번호**: `00`(애플리케이션 서버 이름 `bgissap1_EFX_00`에서 `_00`이 인스턴스 번호)
- **SID**: EFX
- 포트 공식 적용: HTTPS = 443 + 00 = **44300**, HTTP = 80 + 00 = **8000**

STAD(Single Statistical Records)로 들어가면 누가/언제/어떤 트랜잭션으로/어떤 프로그램을 실행했는지가 개별 기록으로 남기 때문에, 남의 abapGit을 쓰지 않고 직접 프로그램을 만들기로 함.

`https://raw.githubusercontent.com/abapGit/build/main/zabapgit_standalone.prog.abap` — abapGit 공식 조직(`github.com/abapGit`)의 `build` 저장소에서 직접 받은 파일을 그대로 다운로드. `ZREPORT_B07` 생성 후, 소스코드 편집 모드에서 Utilities → More Utilities → Upload/Download → Upload로 저장한 파일을 업로드함.

※ `ZREPORT_B07`은 abapGit 공식 저장소의 외부 코드를 그대로 옮긴 설치용 프로그램이라 이번엔 `src/`에 별도 파일로 만들지 않고 이 devlog 기록으로만 남김.
