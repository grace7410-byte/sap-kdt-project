## Classic ABAP 개발

### 102번 헤더 매핑 로직 — 1차 설계
130번 팝업에서 벤더를 선택했을 때 100번 헤더의 구매조직/구매그룹에도 반영되도록 로직을 추가함.

관련 오브젝트: [`ZB07EKKO_F01`](../../src/06_purchase-order/prog/ZB07EKKO_F01.prog.abap) · [`ZB07EKKO_I01`](../../src/06_purchase-order/prog/ZB07EKKO_I01.prog.abap)

```abap
*&---------------------------------------------------------------------*
*& Form get_header_data (130에서 벤더 선택 후 100번 헤더 구매조직/구매그룹 반영)
*&---------------------------------------------------------------------*
FORM get_header_data.
  gs_head-ekorg = gs_vend-ekorg.
  gs_head-ekgrp = gs_vend-ekgrp.

  SELECT SINGLE ekotx FROM zi_b07_ekorg_f4
    WHERE ekorg = @gs_head-ekorg
    INTO @gv_ekorg.
  SELECT SINGLE eknam FROM zi_b07_ekgrp_f4
    WHERE ekgrp = @gs_head-ekgrp
    INTO @gv_ekgrp.
ENDFORM.
```

I01의 `WHEN OTHERS`에서 `PERFORM get_header_data.`와 `PERFORM get_vendor_data USING '' gs_head-lifnr.`를 주석 해제함. 이미 만들어둔 `get_vendor_all_data`가 이유 없이 주석 처리되어 있던 것도 함께 해제함 — I01에 남아있던 다른 주석들은 F01에 실제 구현이 아직 없는 서브루틴들이라 그대로 둠.

### 테스트 — 구매조직/구매그룹 텍스트 불일치 발견
100번, 130번 모두 구매그룹 값 자체는 잘 반영되는데 텍스트가 일치하지 않는 문제를 확인함. 원하는 동작을 정리하면 다음과 같음.
- 130 열 때: `gv_ekorg`/`gv_ekgrp`는 클릭한 벤더 기준 텍스트로 갱신.
- SEL_VEND로 선택: `gs_head-ekorg`/`ekgrp`도 그 벤더 값으로 갱신되고, 텍스트도 이미 벤더 기준으로 갱신되어 있으므로 자연히 일치.
- 취소(선택 없이 닫음): `gv_ekorg`/`gv_ekgrp`를 헤더 자신의 현재 값 기준으로 다시 복원.

### 재설계 — 공용 텍스트 갱신 서브루틴 도입
위 세 가지 케이스를 하나의 서브루틴으로 정리함.

관련 오브젝트: [`ZB07EKKO_F01`](../../src/06_purchase-order/prog/ZB07EKKO_F01.prog.abap) · [`ZB07EKKO_C01`](../../src/06_purchase-order/prog/ZB07EKKO_C01.prog.abap)

```abap
*&---------------------------------------------------------------------*
*& Form refresh_ekorg_ekgrp_text (GV_EKORG/GV_EKGRP 공용 텍스트 갱신)
*&---------------------------------------------------------------------*
FORM refresh_ekorg_ekgrp_text USING pv_ekorg pv_ekgrp.
  " 매칭 실패 시 이전 값이 남지 않도록 반드시 CLEAR 후 조회
  CLEAR: gv_ekorg, gv_ekgrp.

  SELECT SINGLE ekotx FROM zi_b07_ekorg_f4
    WHERE ekorg = @pv_ekorg
    INTO @gv_ekorg.

  SELECT SINGLE eknam FROM zi_b07_ekgrp_f4
    WHERE ekgrp = @pv_ekgrp
    INTO @gv_ekgrp.
ENDFORM.
```

`get_vendor_data`에서 위 서브루틴을 호출하도록 수정하고(기존 2개의 SELECT SINGLE을 대체), `get_header_data`도 이 서브루틴을 호출하는 형태로 단순화함. C01의 `on_hotspot_click`에는 취소(미선택 종료) 시 헤더 자신의 값으로 복원하는 분기를 추가함.

```abap
IF gs_head-lifnr = gs_vend-lifnr.
  cl_gui_cfw=>set_new_ok_code( EXPORTING new_code = 'ENTER' ).
ELSE.
  PERFORM refresh_ekorg_ekgrp_text USING gs_head-ekorg gs_head-ekgrp.
ENDIF.
```

### 테스트 — 정상 반영 확인, 텍스트 필드 길이 확장

## 103/104 화면 생성

### 핵심 설계 결정 (09-03/09-04 확정 사항 재확인)
- 계절(BOMVE) 컬럼 완전 제거 — S-Mobile은 계절성 상품이 아니므로 1기의 `gv_season`/`gv_month` 분기 로직은 2기에 반영하지 않음.
- 방향 반전: 1기는 "원유 1개→완제품 N개" 역BOM(비율 차트)이었으나, 2기는 "부품 N개→완제품 1개" 정방향 조립 BOM. 차트도 "비율"이 아니라 "이 모델 1대당 부품 소요량" 그래프로 의미가 바뀜.
- 3종 비교 대상(104용) = `SM-FOLD`/`SM-FLIP`/`SM-STD`(구 WTI-100/DUBAI-100/MAYA-100 대체).
- 103은 `GV_BASE_PROD`(구 `GV_CRUDE`, 기본값 `'SM-FOLD'` 하드코딩, 화면에서 다른 모델로 직접 변경 입력 가능) 하나의 모델만 보는 차트, 104는 3종 동시 비교(스플리터+ALV+차트) 구조를 그대로 유지.
- 옵션가(103 ALV)는 `gs_vend-lif_uuid` 기준으로 `ZTB07EINA` JOIN `ZTB07EINE`, 환율/외화 변환 없이 EINE의 NETPR/PEINH/BPRME/WAERS를 그대로 사용.

이 설계에 따라 TOP의 BOM 구조체에 `fmeng`/`meins` 필드를 추가함(기존 `gs_bom`엔 `matnr`/`maktx`/`display_text`만 있었음).

관련 오브젝트: [`ZB07EKKO_TOP`](../../src/06_purchase-order/prog/ZB07EKKO_TOP.prog.abap)

103번 Flow Logic은 기존 것을 그대로 유지함.

```abap
PROCESS BEFORE OUTPUT.
  MODULE init_alv_0103.      " 옛 init_alv_0110 — OPTI ALV 초기화
  MODULE init_chart_0103.    " 옛 init_chart_0110 — CHART 렌더링

PROCESS AFTER INPUT.
  " 원본부터 빈 PAI — 그대로 유지
```

O01에 `init_alv_0103`/`init_chart_0103`을 구현하고, F01에 `get_opti_data`(103번 옵션가 ALV 조회)/`set_fcat_opti`(필드카탈로그)/`get_chart_data`(BOM 소요량 조회)/`display_chart`(iXML 차트 렌더링)/`create_chart_object`(커스텀 컨테이너+차트 엔진 생성 공용 유틸)를 신규 작성함.

관련 오브젝트: [`ZB07EKKO_O01`](../../src/06_purchase-order/prog/ZB07EKKO_O01.prog.abap) · [`ZB07EKKO_F01`](../../src/06_purchase-order/prog/ZB07EKKO_F01.prog.abap)

### 103 연결 디버깅 — 화면 표시 순서와 데이터 조회 사이의 순환참조
ALV와 차트가 전혀 표시되지 않는 문제가 발생함. 컨테이너 이름, 변수, Flow Logic, 모듈 생성까지 모두 확인하고 전체 액티브까지 했는데도 `init_alv_0103`/`init_chart_0103`에 디버깅을 걸어보니 아예 진입 자체가 안 되는 것을 확인함.

원인은 `set_dynnr_tab`(O01)의 폴백 조건에 있었음.

```abap
MODULE set_dynnr_tab OUTPUT.
  CASE tabstrip-activetab.
    WHEN 'TAB1'.
      gv_dynnr_tab = '0103'.
    WHEN 'TAB2'.
      gv_dynnr_tab = '0104'.
    WHEN OTHERS.
      gv_dynnr_tab = '0103'.
      tabstrip-activetab = 'TAB1'.
  ENDCASE.

  IF gs_head-lifnr IS INITIAL OR gv_chart_show IS INITIAL.
    gv_dynnr_tab = '9000'.
  ENDIF.
ENDMODULE.
```

`set_dynnr_tab`이 "103번을 보여줄지 9000(빈 화면)을 보여줄지" 판단할 때 `gv_chart_show`를 참조하는데, 그 `gv_chart_show`는 103번이 실제로 화면에 떠서 자신의 PBO(`init_chart_0103`)가 실행되어야만 채워지는 값이었음. 즉 103번은 `set_dynnr_tab`이 통과시켜줘야만 뜨는데, `set_dynnr_tab`은 103번이 떠야 채워지는 값을 조건으로 걸고 있어 순환참조가 발생하는 구조였음.

1차로 `gv_chart_show` 조건만 제거하고 `gs_head-lifnr` 조건은 남겨봤으나 여전히 화면이 뜨지 않았음. 벤더가 없어도 103번 화면 자체는 떠야 하는 것이 맞는 설계였음(1기 `get_opti_data`도 동일한 패턴) — 벤더가 없으면 필터만 안 걸릴 뿐, 전체 벤더의 인포레코드가 조회되어야 하고, BOM 차트는 애초에 벤더와 무관한 데이터라 영향을 받지 않아야 함. 최종적으로 다음과 같이 정리함.

1. O01 `set_dynnr_tab` — 벤더 유무로 9000을 보내는 로직 자체를 삭제(TABSTRIP 분기만 남김).
2. TOP `gs_opti`에 `lif_uuid`/`lifnr`/`name1` 필드 추가(전체조회 시 공급업체 구분 표시용).
3. F01 `get_opti_data` — 벤더 필터를 옵셔널로 전환하고, 전체 조회 시 공급업체를 구분할 수 있도록 `ZTB07LFA1` 조인 추가 + 행 수 제한(`UP TO 100 ROWS`). `set_fcat_opti`에도 LIFNR/NAME1 컬럼을 추가.
4. I01 `WHEN OTHERS` — `get_opti_data` 호출을 `gv_visible` 조건 밖으로 빼서 상시 호출되도록 수정하고, 기존에 사용하지 않기로 한 `gv_visible` 분기 자체를 제거함. 이 김에 이미 만들어둔 `clear_header_data`도 주석을 해제함.

관련 오브젝트: [`ZB07EKKO_O01`](../../src/06_purchase-order/prog/ZB07EKKO_O01.prog.abap) · [`ZB07EKKO_I01`](../../src/06_purchase-order/prog/ZB07EKKO_I01.prog.abap) · [`ZB07EKKO_F01`](../../src/06_purchase-order/prog/ZB07EKKO_F01.prog.abap) · [`ZB07EKKO_TOP`](../../src/06_purchase-order/prog/ZB07EKKO_TOP.prog.abap)

## RAP 개발 — 06 구매오더

Classic ABAP과 별개로, [FS] 06 구매오더 문서를 기준으로 RAP 오브젝트 구축을 시작함.

### Interface View — ZI_B07_EKKO (헤더)
`ZTB07EKKO` 테이블 기준으로 View Entity를 생성하고, 타임스탬프/유저관리 어노테이션을 추가함. 구매정보레코드(공급업체) 데이터를 끌어오기 위해 `_Lfa1` Association을 연결하고, UUID 대신 코드와 이름을 함께 노출하도록 `Lifnr`/`Name1` 필드를 추가함.

관련 오브젝트: [`ZI_B07_EKKO`](../../reference/06_purchase-order.md) · [코드 보기](../../src/06_purchase-order/cds/ZI_B07_EKKO.ddls.asddls)

### Interface View — ZI_B07_EKPO (아이템)
`ZTB07EKPO` 테이블 기준으로 생성함. Parent 연결(`association to parent`)은 Root View(`ZR_B07_EKKO`)가 먼저 만들어져 있어야 성립하므로 우선 주석 처리하고 필수 어노테이션만 추가해 액티브함. FS에 맞춰 자재/구매정보레코드/플랜트/저장위치 Association을 연결하고, 이 화면들에서 UUID 대신 코드·이름을 노출해야 해서 각 Association의 텍스트 필드(`Matnr`/`Infnr`/`WerksText`/`LgortText`)도 추가함. Root View를 만들고 돌아와 parent Association 주석을 해제해 최종 완성함.

관련 오브젝트: [`ZI_B07_EKPO`](../../reference/06_purchase-order.md) · [코드 보기](../../src/06_purchase-order/cds/ZI_B07_EKPO.ddls.asddls)

### Root View — ZR_B07_EKKO
생성 직후에는 Composition을 주석 처리하고 액티브한 뒤, `ZI_B07_EKPO`로 가서 parent 연결을 하고 액티브하고 돌아와야 이 Root View에서도 연결이 확인되는 순서로 진행함.

Composition(`_Ekpo`)을 연결하고, 구매오더 유형(Bsart)의 도메인 텍스트를 `I_DomainFixedValueText` Association(`_BsartText`)으로 끌어옴. 구매그룹(Ekgrp) Value Help는 구매정보레코드 때와 동일하게, 표준 도메인에 이미 붙어있는 기본 서치헬프(`H_T024`)에 밀려 Projection 단 재정의가 먹히지 않아 Root View에 직접 작성함. 이어서 구매조직/구매그룹 텍스트도 `_EkorgText`/`_EkgrpText` Association으로 끌어옴.

이후 회사코드/통화 텍스트를 Projection View(`ZC_B07_EKKO`)에서 Association으로 직접 연결하려다 `Field selection of association _BukrsText is not supported in Projection Views` 오류가 발생함. 텍스트 필드 자체에 대한 정의는 Root View에서 해야 한다는 것을 다시 확인하고, `_BukrsText`/`_WaersText` Association을 Root View로 옮겨 정의함.

관련 오브젝트: [`ZR_B07_EKKO`](../../reference/06_purchase-order.md) · [코드 보기](../../src/06_purchase-order/cds/ZR_B07_EKKO.ddls.asddls)

> ⚠️ `ZR_B07_EKKO`는 devlog에 나뉘어 제시된 두 코드 조각(구매조직·구매그룹 텍스트 추가본 + 회사코드·통화 텍스트를 Root로 옮긴 수정본)을 병합해 재구성했습니다. 실제 최종 코드와 다르면 확인 부탁드립니다.

### Projection View — ZC_B07_EKKO / ZC_B07_EKPO
`define`과 `view entity ZC_B07_EKKO` 사이에 `root` 키워드를 추가하고, 퀵 픽스(Ctrl+1)로 `provider contract` 구문을 자동 생성함. 검색 가능(`@Search.searchable`), 의미적 PK(`@ObjectModel.semanticKey`) 어노테이션을 추가하고, FS의 검색조건 3개(구매오더일/공급업체/구매오더번호)에 Search/UI.selectionField 어노테이션을 달아 상단 검색 필드를 구성함. 공급업체는 이름을 텍스트 필드로 함께 노출하고 서치헬프도 연결함. Sort 조건(구매오더일 최신순 → 공급업체 → 구매오더번호)도 FS 기준으로 맞춤. 회사코드/통화 등 FS 요구사항은 아니지만 필요한 텍스트·서치헬프도 추가함.

가장 주의가 필요했던 부분은 Consumption 뷰끼리 Parent-Child로 연결하는 문법이었음 — `ZC_B07_EKKO`(Header, Parent)에 연결된 `_Ekpo`는 Projection(`ZC_`)이 아니라 Interface(`ZI_`) View라서, `_Ekpo : redirected to composition child ZC_B07_EKPO` 구문을 바로 쓰면 오류가 남. `ZC_B07_EKPO`가 먼저 존재해야 하는 구문이라, 우선 `_Ekpo`만 있는 상태로 액티브해 두고, `ZC_B07_EKPO`를 만들어 `redirected to parent`로 연결·액티브한 다음 돌아와 위 redirect 구문으로 바꿔주는 순서로 진행하기로 함 — `ZC_B07_EKPO` 자체는 아직 생성 전이라 다음 작업으로 남김.

## 오늘 배운 점 / 막힌 점
- PBO에서 "어떤 화면을 보여줄지" 판단하는 로직이, 그 화면 자신이 떠야만 채워지는 값을 조건으로 참조하면 순환참조가 발생해 화면이 영영 뜨지 않는다.
- Projection View에서 Association 기반 텍스트 필드를 직접 정의할 수 없는 경우가 있고(`Field selection of association ... is not supported in Projection Views`), 이런 텍스트 정의는 Root View로 올려야 한다.
- Composition Redirect(`redirected to composition child`)는 대상 Child Projection이 먼저 존재해야 문법이 성립한다.
