## RAP 개발 — 05 구매정보레코드

### SetVendorMaterialUuid — sy-subrc 공유 버그 수정
LFA1/MARA를 순서대로 `READ TABLE`한 뒤 `sy-subrc`를 한 번만 확인해 LifUuid/MatUuid를 채우고 있었는데, 두 번째 `READ TABLE`(MARA)의 `sy-subrc`가 첫 번째(LFA1) 결과를 덮어쓰는 바람에 LifUuid COND가 실제로는 MARA 조회 성공 여부를 보고 있던 버그를 발견함. LFA1/MARA 조회 성공 여부를 각각 `lv_lfa1_found`/`lv_mara_found`로 분리 추적하도록 수정.

```
READ TABLE lt_db_lfa1 INTO DATA(ls_db_lfa1) WITH KEY lifnr = ls_eina-Lifnr.
DATA(lv_lfa1_found) = xsdbool( sy-subrc = 0 ).

READ TABLE lt_db_mara INTO DATA(ls_db_mara) WITH KEY matnr = ls_eina-Matnr.
DATA(lv_mara_found) = xsdbool( sy-subrc = 0 ).

APPEND VALUE #( %tky = ls_eina-%tky
  LifUuid = COND #( WHEN ls_eina-LifUuid IS INITIAL AND lv_lfa1_found = abap_true
                     THEN ls_db_lfa1-lif_uuid ELSE ls_eina-LifUuid )
  MatUuid = COND #( WHEN ls_eina-MatUuid IS INITIAL AND lv_mara_found = abap_true
                     THEN ls_db_mara-mat_uuid ELSE ls_eina-MatUuid )
) TO lt_update.
```

다만 이건 sy-subrc가 잘못된 대상을 보고 있던 버그를 고친 것일 뿐, 예전부터 남아있던 "존재하지 않는 Lifnr/Matnr 값을 넣어도 에러 없이 그냥 통과되는" 문제 자체는 이번에도 손대지 못함 — 여전히 미착수.

핸들러 클래스명도 `lhc_zr_b07_eina` → `lhc_eina`로 바꿈(아이템 쪽 `lhc_eine`과 이름 패턴 맞춤, 기능엔 영향 없음).

관련 오브젝트: [`ZR_B07_EINA`](../../reference/05_purchase-info.md) · [코드 보기](../../src/05_purchase-info/bimp/zbp_r_b07_eina.clas.abap)

### draft determine action Prepare — 빈 블록 발견
BDEF의 `draft determine action Prepare { }`가 빈 채로 남아있는 걸 발견함. `on save` Validation 자체는 걸려 있어 실제 저장 시 검증은 됐겠지만, Fiori Draft 화면에서 저장 누르기 전에 실시간으로 에러를 보여주는 동작은 지금까지 꺼져 있었던 셈. 06 구매오더 bdef에 이미 있는 패턴과 동일하게 `CheckRequired`/`CheckDuplicate`/`CheckEsokz` 3개를 등록함.

## RAP 개발 — 06 구매오더

### 헤더 삭제표시(Loekz) 필드 컨트롤 마무리
BDEF 헤더 필드 목록엔 이미 `field(features:instance) Loekz, Waers;`로 Loekz가 동적 제어 대상으로 선언돼 있었는데, 정작 `get_instance_features` 메서드엔 `%field-Loekz` 로직이 구현돼 있지 않은 상태였다(구현 누락). 한 차례 "다시 FS 보니" 하면서 Loekz를 정적 `readonly`로 되돌릴지 고민했으나, `SetDeletionFlag` 액션(FS p.15-16 — 저장된 구매오더 삭제는 Object Page 버튼으로만 처리)과 마찬가지로 삭제표시도 PO가 채번(저장)된 후에만 의미가 있다고 결론 내려 되돌리지 않고 인스턴스 피처 제어를 그대로 유지하기로 함. Ebeln 채번 여부 기준(채번 후=편집 가능, 전=읽기전용)으로 `%field-Loekz`를 추가.

```
%field-Loekz = COND #( WHEN ls_ekko-Ebeln IS NOT INITIAL
                        THEN if_abap_behv=>fc-f-unrestricted
                        ELSE if_abap_behv=>fc-f-read_only )
```

### 헤더 CheckRequired — LifUuid → Lifnr
헤더 `CheckRequired`가 백엔드 FK(LifUuid)를 검사하고 있어, 05번 구매정보레코드에서 이미 겪었던 것과 같은 문제(화면엔 값이 입력됐는데 UUID는 아직 안 채워진 상태라 항상 필수값 에러가 남)가 재현될 수 있는 상태였음. 화면 입력 필드 기준인 Lifnr을 검사하도록 수정.

### 아이템 Postat 필드 컨트롤 추가
Postat(구매오더상태)을 신규로 동적 제어 대상에 추가. Waers와는 반대로, 이미 DB에 저장된 아이템은 편집 가능/신규 생성 중인 아이템은 읽기전용이 맞다고 판단해 BDEF에 `Postat`을 `features:instance`로 추가하고, `get_instance_features`에 Waers COND와 반대 조건으로 `%field-Postat`을 추가함.

```
field ( features : instance ) Elikz, Waers, Postat;
```
```
%field-Postat = COND #( WHEN line_exists( lt_db_ekpo[ ebeln_uuid = ls_ekpo-EbelnUuid
                                                        ebelp      = ls_ekpo-Ebelp ] )
                         THEN if_abap_behv=>fc-f-unrestricted
                         ELSE if_abap_behv=>fc-f-read_only )
```

아이템 `CheckPositiveQty`의 메시지 번호도 `022`→`023`으로 변경함.

## Classic ABAP 개발 — 06 구매오더

### 103번 옵션가 → 100번 아이템 반영
103번 옵션가 ALV 툴바에 "아이템 추가" 버튼(`on_toolbar`)을 달고, 클릭 시 선택된 옵션가 행들을 100번 아이템 ALV의 빈 줄에 채워 넣는 `add_selected_data`를 구현함(`on_user_command`의 `ADD_OPTI` 케이스에서 호출). 자재/구매정보번호/플랜트/단위/단가/통화를 옵션가 행에서 그대로 끌어옴.

### 103번 "기준 모델" 리스트박스
BOM 차트 기준이 되는 완제품(FERT)을 고르는 VRM 리스트박스(`set_base_prod_listbox`)를 구현하고, O01에 이를 호출하는 `SET_BASE_PROD_LISTBOX` OUTPUT 모듈을 신규로 추가함(SE51 "Value List" 필드 ID `GV_BASE_PROD`와 일치시켜야 함).

### 저장 전 확인 팝업(confirm_save)
100번 저장(SAVE) 흐름에 저장 전 확인 팝업을 연결함. 처음엔 `gv_name1`에 발주번호(Ebeln)가 표시되는 줄 알고 그대로 썼으나, 애초에 `gv_name1`엔 Ebeln이 들어갈 자리가 아니었다. 화면에서 값이 표시되지 않아 확인해보니, 표시하려던 정보는 `Lifnr`(공급업체) 쪽이 맞았다. 메시지 문구를 `gs_vend-lifnr` 기준으로 수정.

`lv_total`(총액)은 표시하지 않기로 했다. 기존 ALV 단가/총액 필드 로직이 통화 변환(SAP 표준 FM 미사용) 없이 값을 그대로 올리고 있어 소수점부터 계산이 맞지 않는 상태였고, 틀린 값을 그대로 노출할 필요는 없다고 판단해 계산 코드는 남기고 화면 표시만 제외했다. 추후 프로그램을 더 개발하게 되면 통화 변환 로직부터 수정하고 총액 표시도 되살릴 예정.

I01의 `SAVE` 케이스에서 `PERFORM confirm_save CHANGING gv_answer.` 주석을 해제해 실제 호출 경로를 연결함.

관련 오브젝트: [`ZB07EKKO_C01`](../../reference/06_purchase-order.md) · [`ZB07EKKO_F01`](../../reference/06_purchase-order.md) · [`ZB07EKKO_O01`](../../reference/06_purchase-order.md) · [`ZB07EKKO_I01`](../../reference/06_purchase-order.md)

## 오늘 배운 점 / 막힌 점
- BDEF에 `field(features:instance)`로 선언만 해두고 `get_instance_features`에 그 필드의 `%field-X` 로직을 실제로 구현하지 않으면, 선언은 살아있어도 동작은 하지 않는 반쪽짜리 상태로 남는다 — 선언과 구현을 함께 확인해야 한다.
- `READ TABLE`을 연달아 두 번 쓰면서 `sy-subrc`를 한 번만 확인하면, 뒤의 `READ TABLE` 결과가 앞의 것을 덮어쓴다 — 각 조회의 성공 여부를 즉시 별도 변수로 받아둬야 한다.
- `draft determine action Prepare`가 비어있어도 `on save` Validation 자체는 저장 시 정상 동작한다 — 다만 Fiori Draft 화면의 저장 전 실시간 검증(입력 중 에러 표시)은 Prepare에 등록된 것만 동작한다.
